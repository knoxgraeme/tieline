NASA-inspired guardrails for autonomous coding agents

A codebase agents can safely maintain needs two mutually reinforcing layers: constrained code shapes that are easy to analyze, and an evidence system that constrains what changes mean, prove, and permit.

Codebase Context

Correction incorporated: code-shape discipline is not secondary. Its real value is analyzability—reducing hidden control flow, unbounded resource use, non-local state, unchecked failures, and indirection. Those properties help static tools and coding agents for the same reason: fewer plausible interpretations and fewer reachable failure states.

What Tieline already does well

Approved product-context checksums, explicit coverage, deterministic shard merge, path validation, immutable history, runtime schemas, database constraints, and separate writer/approver credentials are strong assurance primitives.

The planned next layer

The living-spec plan adds acceptance criteria, test links, a committed manifest, and deterministic path-level drift. It correctly moves the product from “where behavior lives” toward “what it should do.”

The important semantic gap

The plan currently defines verified structurally—a test link exists—and defers test-result evidence. A link proves association, not adequacy, execution, freshness, or independence.

The important code-shape gap

The repository enables TypeScript strict, but package scripts expose no linter or second static analyzer. Several core modules are large, and no explicit machine-enforced complexity, indirection, bounded-async, or error-contract profile exists.

NASA’s broader engineering guidance supplies what Power of 10 alone does not: bidirectional traceability, objective evidence, validation distinct from verification, off-nominal behavior, risk-based tailoring, independent V&V, controlled waivers, formal entry/exit criteria, and runtime assurance for autonomous systems. The strongest design uses both levels.

1

Agent Power of 10 for TypeScript

Code shapeConfidence 95%Complexity Medium
Description

Define a deliberately small, enforceable TypeScript rule set: simple control flow; bounded retries, concurrency, queues, and result sets; small single-purpose functions; explicit invariants and recovery; narrow state and capability scope; checked results and validated inputs; restricted reflection, dynamic dispatch, and type escapes; bounded indirection; and zero compiler, linter, or static-analysis warnings. Enforce it on changed code first, then ratchet the existing baseline.

Basis · direct

Power of 10 was created to remove constructs that defeat code review and static analysis. This repository has strict TypeScript and strong runtime schemas, but no visible lint/static-analysis gate beyond compilation.

Rationale

Agent-maintainable code is code whose relevant control flow, state, bounds, and contracts are locally visible. This shrinks the reasoning problem for tools, reviewers, and models simultaneously.

Downsides

Naive numeric limits invite gaming. Generated code, UI adapters, and query repositories need explicit tailoring; the governing metric should be local comprehensibility, not aesthetic uniformity.

The two-layer model

2

Living assurance graph

Intent graphConfidence 92%Complexity High
Description

Evolve story → acceptance criteria → tests → code into a typed graph of claims, assumptions, prohibited outcomes or hazards, verification methods, objective evidence, code, tests, waivers, and decisions. Compute orphan, stale, contradicted, and insufficiently evidenced states from graph relationships rather than manually declaring them.

Basis · direct

The living-spec plan identifies missing acceptance-criteria/test linkage. NASA SWE-052 requires bidirectional traces and explicitly uses them to detect both unimplemented user needs and extra system behavior with no justified parent.

Rationale

This turns semantic intent from retrieval context into a machine-checkable assurance structure. It also gives deterministic drift and change-impact analysis a principled substrate.

Downsides

The schema and migration cost is high. The graph becomes ceremony if its first slice does not immediately answer useful questions in CI and agent workflows.

From a link chain to a defensible claim

3

Mission-scoped assurance envelope

ExecutionConfidence 87%Complexity High
Description

Give every autonomous run a machine-readable envelope: intended claims, allowed paths and mutation classes, forbidden effects, capability and tool leases, resource budgets, expected evidence, checkpoint policy, and a safe stopping state. A supervisor monitors the run; a postflight check compares actual mutations and evidence to the declaration.

Basis · external + reasoned

Power of 10’s fixed bounds make execution analyzable. NASA runtime-assurance work adds the autonomous-system pattern: monitor a complex or untrusted controller and intervene before a protected property is violated.

Rationale

Long-running agents need controls during execution, not only review after completion. The envelope makes scope drift, capability creep, repeated failure, and ambiguous partial work observable.

Downsides

Requires run telemetry, interruption semantics, and recoverable checkpoints. Tight envelopes can cause false stops; loose ones become decorative.

4

Negative intent and off-nominal behavior

EvidenceConfidence 90%Complexity Medium
Description

Add first-class “must not,” hazard, boundary-condition, recovery, and known-safe-state clauses beside positive acceptance criteria. Require high-risk changes to trace these clauses to explicit negative and off-nominal tests.

Basis · external

NASA IV&V asks separately whether software avoids unintended behavior and responds correctly under adverse conditions. Hazardous requirements are derived into nominal, abnormal, and off-nominal tests.

Rationale

Agents naturally optimize for the requested happy path. Prohibited outcomes supply semantic boundaries and focus test generation on costly omissions.

Downsides

Hazard language can become inflated in ordinary product code. Apply it by risk profile and insist on concrete observable outcomes.

5

Independent evidence pipeline

Evidence + governanceConfidence 89%Complexity Medium
Description

Separate implementation, semantic validation, and technical verification. The implementing agent cannot author the only success evidence or declare completion; completion is derived from required evidence and signed by a deterministic check, distinct verifier context, or human according to risk.

Basis · direct

Tieline already prevents the MCP writer from approving its own proposals. NASA IV&V treats technical independence as additive because self-verification misses different classes of error.

Rationale

This generalizes one of the repository’s strongest existing boundaries from database approval to the whole change-and-assurance loop.

Downsides

Independent contexts cost time and tokens and can still share a bad specification or flawed toolchain. Independence improves confidence; it does not create truth.

6

Risk-tiered assurance profiles with expiring waivers

Evolution + governanceConfidence 88%Complexity Medium
Description

Classify behavior or change impact into a few profiles that select required code-shape checks, evidence types, negative tests, reviewer independence, execution budgets, and approval. Any tailored-out rule becomes a scoped, justified, mitigated, approved, expiring waiver with revalidation triggers.

Basis · external

NASA varies assurance rigor by software criticality and requires tailoring or waiver rationale, accepted risk, mitigation, and the appropriate authority.

Rationale

Uniform maximum rigor will not survive ordinary development. Explicit proportionality preserves strict controls where they matter without teaching agents and teams to bypass the whole system.

Downsides

Risk can be gamed downward. Defaults, automatic escalation signals, and waiver visibility must be conservative.

7

Adaptive guardrail laboratory

EvolutionConfidence 82%Complexity Medium
Description

Treat the guardrails as software under test. Maintain seeded bad changes, mutation tests, policy-bypass attempts, stale-evidence cases, and synthetic scope creep; measure catch rate, false positives, escape rate, and time-to-disposition. Feed real escapes back into change-class checklists.

Basis · external + reasoned

NASA formal-inspection guidance evolves checklists from recurring escaped defects. Assurance guidance also treats tool output and objective evidence as artifacts whose credibility matters.

Rationale

Autonomous agents will discover accidental loopholes even without adversarial intent. An untested guardrail suite eventually becomes compliance theater.

Downsides

Needs a representative corpus and ongoing curation. Synthetic violations can overfit controls to known patterns.
